# honest-boot: the client bootloader (component spec)

honest-boot is the composition root of the client tier. On page load it turns the declared `h*-`
attributes in the server-rendered HTML into live behaviour: it finds them, reads each one,
loads the module that owns it, initialises that module against the DOM, and then keeps doing the same
as HTMX or other code swaps new HTML in. It reads the page; it holds no state of its own.

Its ancestor is the genX universal bootloader (`genX/src/bootloader.js`); this spec rebuilds that
pipeline in the Honest world — DOM watching through honest-DOM, and a declared, locally-owned attribute
vocabulary that both resolves each attribute at runtime and makes the whole surface checkable before it
runs. It does no type-classification of untrusted input; that is a server concern (honest-type at the
request boundary). The front end only reads and resolves values the developer already declared. The
framework-level summary is in `../01-framework/honest-framework-spec.md` ("Bootloader Architecture");
this is the module contract.

## 1. Purpose

The `h*-` attributes in a page are a promise: "this element behaves this way." honest-boot is what
keeps that promise at runtime, and its design is what makes the promise *checkable* at commit time.
Because the HTML is generated by the templates or the serve code, the complete set of `h*-` attributes
a page can carry is knowable ahead of time (see **closed** in the glossary). honest-boot's attribute
vocabulary is declared locally as data, so honest-check can verify — pre-commit, offline — that every
`h*-` attribute a template emits resolves to a real module and a value the declared vocabulary lists.
The bug category this eliminates: the element that looks wired but is inert — the dead button.

## 2. Working terms

- **`h*-` attribute.** A declared honest attribute on an element, of the form `h<x>-<name>` (`hf-format`,
  `hd-draggable`), that names a behaviour a module provides. Distinct from HTMX's `hx-` attributes,
  which honest-boot does not own and does not touch.
- **Attribute vocabulary.** The closed, locally-declared table mapping each honest prefix to the module
  that owns it (`hf` → honest-format, `hd` → honest-drag, …). The source of truth for what is valid
  (§3). Declared as data, never inferred (the HC-REF004 pattern).
- **Module registry.** Where each module's code is fetched from at runtime — a local path or a CDN URL
  per prefix. Distinct from the vocabulary: the vocabulary says what is *valid*, the registry says where
  the *code* lives.
- **honest.bridge.** The single shared DOM observer honest-boot subscribes to, provided by honest-DOM
  (`observe`/`on`). One observer for the whole page, not one per module.

## 3. The attribute vocabulary is declared locally; the CDN hosts the code

The set of valid honest prefixes and the module each maps to is **declared in the repository as data**
— the source of truth. honest-boot and honest-check both resolve against it. The module code is served
from the module registry (a local path or a CDN URL).

**Where it lives, and why.** The vocabulary is part of the successor to genX: the front-end runtime whose
whole job is to do formatting and presentation on the client — `hf-format="currency"` turns a raw
`1299.99` the server sent into `$1,299.99` in the browser — so the backend never touches presentation
and stays pure. The `h*-` modules and their vocabulary therefore belong to the client tier, not the
Python backend. Because two different things read the same table — honest-boot (JavaScript, at runtime)
and honest-check (Python, scanning the templates pre-commit) — the vocabulary is a **language-neutral
declared data file** (e.g. JSON), not code in either language. It is declared as data, never scraped
from the modules' source (the HC-REF004 rule).

The separation is deliberate, and follows principles the framework already holds:

- **Declared, never inferred.** What is valid is a table a human wrote and a reviewer can read, not
  whatever a remote source happens to serve at check time. This is the same decision as HC-REF004,
  where genX's `fx-*` vocabulary is declared as data and never scraped.
- **The gate stays hermetic.** Resolving a template's `h*-` attributes against the local vocabulary
  needs no network, so the pre-commit check always runs offline and two runs agree. honest-check *may*
  read the module registry (including a CDN) to confirm a declared module actually resolves there — a
  reference-resolution check, like the dead-link checks for `hx-get`→route and `class`→CSS — but it is
  never *governed* by the CDN. Reaching out to confirm is allowed; depending on it to know what is valid
  is not (see **closed** in the glossary — closure is static knowability, not runtime isolation).
- **Single source of truth.** One table both the checker and the runtime use means a template cannot
  emit an attribute that resolves at runtime but not in the check, or the reverse.

## 4. The pipeline

The pipeline is the genX bootloader's, rebuilt honest. The pure steps are functions of their input;
the effectful steps are the boundary. This is the same split genX draws (`scan`/`detectPrefix`/`parse`
pure; `load`/`init`/`observe` at the boundary).

**Pure (input in, output out):**

1. **scan(root, vocabulary) → elements.** Find every element under `root` carrying a declared honest
   attribute. The selector is built from the declared vocabulary — a closed set, not an `h*` wildcard —
   so HTMX's `hx-` and any non-declared attribute are ignored.
2. **resolve(element, vocabulary) → prefix.** Which module owns the element's honest attribute.
3. **read(element, vocabulary) → config.** Read the honest attribute's declared value and produce the
   config to hand the module. This is a lookup, not a classification: the attribute value is something
   the developer wrote from the closed declared vocabulary (`hf-format="currency"`), not untrusted input,
   so honest-boot resolves it against the declared list — it does not type unknown input. (Type
   classification of *untrusted* input is a server concern, honest-type at the request boundary; it has
   no place on the front end, whose whole job is presentation of already-declared values.) The surface
   may be written in more than one notation (verbose, colon, JSON options, class form); each notation is
   a way of writing the same declaration and all resolve to the same config.

**Boundary (I/O — the only steps that touch the network, the DOM, or the event log):**

4. **load(prefix, registry) → module.** Dynamically import the module for each needed prefix from the
   registry. Only the modules a page actually uses are loaded. Whether the import is lazy or eager, local
   or from a CDN, is an implementation choice — it does not affect what is knowable pre-commit (§3).
5. **init(module, element, manifest).** Initialise the module against the DOM. DATAOS: prefer the
   module's "read your state out of the DOM" entry point over one that needs pre-built data, because the
   DOM is the state store.
6. **observe / rescan.** Subscribe once to honest.bridge (honest-DOM's shared observer). When HTMX or
   other code swaps in new HTML, rescan the swapped subtree and load/init any newly-needed module — the
   fix for "content inserted after load never gets enhanced."
7. **emit `hf.browser.classify`.** One honest-observe event per element honest-boot resolves (honest-observe
   §4.8), automatically, with no developer code. (`hf.browser.classify` is the event's declared name in
   honest-observe; it records that honest-boot handled the element, not a type-classification.)

## 5. Static checkability (the poka-yoke)

Because §3 gives honest-check a local vocabulary and §1 gives it template-generated HTML, honest-check
verifies, pre-commit and offline, that:

- every `h*-` attribute a template emits names a prefix in the declared vocabulary, and
- each attribute's value is one the declared vocabulary lists (a valid declared value, not a typo).

An attribute that names no declared prefix, or a value the vocabulary does not list, is the dead button —
reported at the gate, before the page ever runs. This is the client-side counterpart of the existing
`hx-get`→route and `class`→CSS reference checks.

## 6. Invariants

- **I1. The vocabulary is declared locally and is the source of truth.** Runtime resolution and the
  pre-commit check read the same declared table. The CDN may be *read* to confirm code resolves, never
  to *decide* what is valid.
- **I2. The scanner matches the closed declared set, not a wildcard.** `hx-` and any undeclared
  attribute are ignored, so honest-boot and HTMX never collide.
- **I3. One shared observer.** All rescanning goes through honest.bridge; honest-boot creates no observer
  of its own.
- **I4. Pure core, boundary edges.** scan/resolve/read are pure; load/init/observe/emit are the
  boundary. Reading resolves a declared value against the declared vocabulary; it is not type-
  classification of untrusted input — that is the server's honest-type job and has no place on the front end.
- **I5. DATAOS init.** Modules initialise by reading state from the DOM; honest-boot passes no separate
  state store.

## 7. Inputs

1. **The server-rendered HTML** (from the templates or serve code) — the closed input surface.
2. **The declared attribute vocabulary** (§3) — prefix → owning module, and the values each allows.
3. **honest-DOM** — the shared observer (honest.bridge) and the `hf.browser.classify` emit path.
4. **The module registry** — where each module's code is fetched at runtime.

honest-type is deliberately NOT an input: the front end resolves already-declared values, it does not
type untrusted input.

## 8. Placement, dependencies, and order

honest-boot is JavaScript, in the application-production (client) tier, alongside honest-DOM,
honest-format, and honest-components. It is the composition root, so it comes **last** in the client
tier: it depends on honest-DOM (observe/emit) and the modules it loads (honest-format, honest-components,
and any other `h*-` module). It does **not** depend on honest-type — classification of untrusted input
is a server concern, and the front end only resolves already-declared attribute values. It is
dev/runtime client code, not a build-time tool.

## 9. Conformance

honest-boot is gated like every JS module (`javascript/gate.sh`): honest-check (JS rules) clean, its
`test/*.test.js` and `conformance/` (`suite.json` + `run.js`) green under coverage, one gherkin
scenario per function (`javascript/feature-gate.sh`), and mutation adequacy (`javascript/js_mutate.py`,
equivalents declared in `conformance/mutants_setaside.json`). The pure steps (scan, resolve, read
mapping, selector building) are exhaustively tested from the declared vocabulary; the boundary steps
(load, init, observe, emit) are tested through injected plugs, the same way honest-DOM tests its
`sendBeacon`/observer boundary.

**Real-browser conformance runs under Playwright** (headless). The unit gate above proves the pure steps
and the boundary steps in isolation; the Playwright suite proves the end-to-end binding — a real page
loads, the scan finds real attributes, real modules load and init, an HTMX swap triggers a real rescan,
and `hf.browser.classify` fires. This is the same headless-browser mechanism honest-DOM now adopts, so
the browser harness is shared, decided once for both. The Playwright suite is part of completing the
module (it comes after the unit gate is green), not a substitute for the pure/boundary unit tests.

## 10. Open items

- **The declared vocabulary's exact filename.** Settled (§3): a language-neutral declared data file in the
  genX-successor client tier, read by both honest-boot and honest-check. Only the exact path is left, and
  it is fixed when the honest-check template-scan (§5) is implemented, so the file sits where the checker
  reads it.
- **Notation set.** All genX notations (verbose, colon, JSON, class) are carried; each resolves through
  the declared-vocabulary lookup. The notation grammars belong to the genX-successor front end,
  referenced not redefined here.
