# Rewrite notes: Honest Framework spec, opening

The new opening replaces **lines 1–224** of `honest-framework-spec.md` (the title through the end of "The Patterns and the Implementations," including that section's closing horizontal rule). The remainder of the spec is unchanged. The original file is untouched.

## What changed, and why

- **`.hd` is defined before it is used.** In the old opening it first appeared mid-IDE section, already assumed. A new section, "The `.hd` Declaration," states what the file is, what it declares, the rule "declared, never inferred," that honest-check's conformance tier (rule `HC-REF005`) verifies the code against it, that the universal tier still fires with no `.hd` present, that conformance is opt-in and the file is never a runtime dependency, and that the order of work is spec, then `.hd`, then a failing test, then code. The grammar is pointed at `../02-code-quality/honest-design-architecture.md`.
- **The four-column model is stated early**, in its own section, before the Explorer or the patterns. I/O at the edges, orchestrators above the pure core, work running from input to output. Role keywords (`boundary_in`, `reader`, `orchestrator`, `fn`, `boundary_out`, and `edge`) are named here. The layout follows the Architecture Explorer (Adam chose it over the four-column strip on 2026-09-02, "the only view"). An output boundary is a terminus that calls nothing, which is the Explorer's rule (see discrepancies below).
- **The two Origin sections are merged.** "Origin: One Observation" (DATAOS) and the later "Origin" (the book, the repositories) are now one section. The first-person observation is kept. The historical half is kept, including the repository table. The old wording "the author had already built most of the framework" is recast as "most of the framework had already been built," so the section does not switch from "I" to "the author."
- **Vision, product, licensing, and implementation detail are no longer interleaved.** Definition, Origin, Vision, the four-column model, and `.hd` come first. Apophasis is unchanged in substance (punctuation tightened; em dashes converted to commas and periods). The Third Pillar is retitled "the Architecture Explorer," names the product correctly, and states the open-versus-commercial line from the Explorer README: format, reader, and static renderer are open; the interactive design surface is commercial, in development, sold per seat and per organization, and protected by trademark, the composition-interaction patent, and certification, not by the format. Skeleton languages are the Explorer's list (Python, JavaScript, TypeScript, Go, Java, Rust, Ruby). Two audiences are kept, condensed. The longer IDE path (polymorphic engine, LSP clients, Claude skills, standalone destination) is one paragraph, not a product brief.
- **Lifted from the opening, not discarded.** These belong later, if they still stand:
  - The Skill Registry, skills 0–34, including the proposed `.hd` primitives `transitions` and `schedule` (see open questions), the genX attribute pattern, and the plugin-marketplace distribution.
  - The Rust commitment for the polymorphic core (statically linked per-platform binaries, vendored under `.honest/bin/` or downloaded at a pinned version, adapter FFI).
  - The LSP performance budgets (single-digit milliseconds warm startup, 20–50ms cold, under 20ms per-keystroke diagnostic, under 200ms initial scan of 20 modules).
  - The game-engine analogy for the two-audience split, and the historical claim that mainstream frameworks never made that split.
  - The Neonto-principle wording that a Python programmer and a Ruby programmer get the same diagram, diagnostics, workspace, and skills, differing only in emitted code (the principle itself remains in "The Patterns and the Implementations").
- **The Patterns and the Implementations are kept**, with a light pass only (the cross-reference "See 'The Third Pillar' below," which pointed at a section already above it, is gone; "honest framework" in the Honest Code cell is now "The Honest Framework"; "enterprise mandated" is hyphenated). The pattern essays and the implementation table are otherwise the original text. Later sections still depend on them.
- **No facts, numbers, dates, or features were invented.** Version, date, and author on the title block are unchanged (0.1 Draft, March 10, 2026). Where the Explorer and `honest-design-architecture.md` disagree, the opening follows the Explorer.

## Discrepancies: Architecture Explorer vs. `honest-design-architecture.md`

The Explorer is treated as authoritative, per Adam. The design-architecture document is still the normative grammar the opening points to; these are the places the two currently disagree, or where the design-architecture document disagrees with itself.

1. **Output boundary as a terminus.** Explorer (`build-map.py`, "The rules the checker enforces"): "An output boundary is a terminus; it calls nothing." Design architecture §2: "A `boundary_out` may call pure functions and other output boundaries. It may not invoke an orchestrator, a chain, or an input boundary." The opening follows the Explorer.
2. **Who may declare a `side_effect`.** Design architecture §2 says only a `boundary_in` or `boundary_out` may name a `side_effect`. That is too narrow: a `reader` declares `side_effect reads`, and an orchestrator that keeps a `store` declares `side_effect reads_writes "store:NAME"`. The validator section of the same document is more careful ("A plain `fn` declares no `side_effect`"). The Explorer agrees with the validator, not with §2. The opening says a plain `fn` declares no side effect, and does not repeat the §2 overclaim.
3. **Section 2 repeats a paragraph.** The paragraph beginning "The four columns are the functions. `.hd` also names the data those functions move..." is pasted twice in a row. A known flaw, not yet fixed in the source copy.
4. **Visual layout.** Design architecture §2 presents four columns left to right, with orchestrators as column 2 between the input boundary and the pure functions. The Explorer (and design architecture §1 and §7) places the orchestrators above the pure core, boundaries at the edges. Adam chose that layout over the four-column strip on 2026-09-02 and asked that it be the only view. The opening describes the Explorer's layout, still under the established name "four-column model."
5. **`void` vs. `NOTHING`.** Design architecture §3.2 lists `void` among the scalar types. The Explorer's rules and cards speak of `NOTHING` throughout. The opening names neither.
6. **An `entry` naming an orchestrator.** The Explorer accepts it as the thing that launches the orchestrator. A comment in `build-map.py` (at the `ROLES` table) records that "frame's entry-check calls the same entry a missing door" and that "that disagreement predates this table and is not settled." The opening does not take a side.
7. **Proposed grammar that is not in the current format.** The old Skill Registry proposed a `transitions` primitive and a `schedule` primitive in the `.hd` grammar. The current design-architecture document has neither. It says a state machine is expressed as a type record plus its transition functions, "not a dedicated primitive." Those proposals went out with the skill list and should not be read as present in the format.

Two items that look like conflicts but are not, or are already settled:

- **Layer vocabulary.** Design architecture closes the list as `foundation`, `correctness`, `data`, `domain`, `application`, `ui`, `tooling`, and says the order of the list is the stack order. The Explorer once kept its own `SYSTEM_LAYERS` (which omitted `correctness`). That copy was deleted on 2026-10-22; the map now reads `LAYERS` home from honest-design.
- **`awaited`.** The request file `REQUEST-a-card-cannot-say-you-must-await-it.md` asked for a word on the card. It is now in the format (design architecture §3.2) and the Explorer draws it. Historical, not a live disagreement.

## Open questions for Adam

1. Should the design-architecture document be amended so an output boundary "calls nothing," matching the Explorer, or should the Explorer be relaxed to allow a `boundary_out` to call pure functions and other output boundaries?
2. Should design-architecture §2 be corrected so it no longer says only `boundary_in` and `boundary_out` may name a `side_effect`, and should the duplicated paragraph in that section be deleted?
3. Is the conceptual model still "four columns" (the IR still derives `column` 1–4 from the role), even though the only drawn view is boundaries at the edges and orchestrators above the pure core? The opening uses both the name and the Explorer's layout.
4. Do `transitions` and `schedule` still belong in a future grammar, or is the design-architecture position (state machines as types plus functions; no dedicated primitive) the decision?
5. The `entry`-naming-an-orchestrator disagreement (Explorer vs. frame's entry-check) is recorded in the Explorer and marked unsettled. Which way should it go?
6. `void` or `NOTHING` for a function that returns no value? The two sources use different words.
7. The Skill Registry (skills 0–34), the Rust implementation commitment, and the LSP performance budgets were lifted from this opening. Do they still stand, and if so, where should they live (a later tooling section, a companion document, the Explorer README)?
8. The opening's host-language lists are taken from different layers and are not the same: four-column portability names Python, JavaScript, Ruby, PHP, Elixir, and Go (design architecture §2); design-surface skeletons are Python, JavaScript, TypeScript, Go, Java, Rust, and Ruby (Explorer README); the implementation table is Python, Pure JS, React, Ruby, PHP, and Elixir. Should these be reconciled, or is each list correct for its layer?
9. The title block is still Version 0.1 (Draft), March 10, 2026. Should a revised opening carry a new draft date?
